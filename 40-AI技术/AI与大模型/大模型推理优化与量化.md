# 大模型推理优化与量化

> [!摘要] 摘要
> 本文聚焦大语言模型上线前后的两大性能抓手——**推理优化**与**量化**，系统梳理其基础概念、核心机制、可落地的工程步骤与常见坑位。推理优化围绕「提高吞吐、降低延迟」展开，核心手段包括连续批处理、PagedAttention、KV Cache 量化与前缀复用、投机解码等；量化则按权重量化与 KV Cache 量化两条线分别处理，并区分 AWQ/GPTQ/GGUF/FP8/MXFP4 等格式的适用硬件与引擎。本文是 [[AI与大模型-从入门到精通]] 体系下「部署与服务化」方向的落地篇，适合需要把大模型真正跑稳、跑快、跑省的工程师。

## 二、基础概念

**推理优化的目标**：在给定硬件下，用更少的显存与更低的延迟，服务更高的并发吞吐。LLM 服务延迟可拆为 **TTFT（Time To First Token，首 token 延迟）** 与 **TPOT（Time Per Output Token，每 token 延迟）**，两者优化手段不同，排查时需分开看。

**两个必须分开理解的优化对象**：

- **权重（Weights）**：模型参数本身，通常在部署前量化一次，不随请求变化。
- **KV Cache**：自回归解码时缓存的历史 token 的 Key/Value 向量，随序列长度与并发数增长，是运行时显存的主要来源。

> [!warning] 关键认知
> **压缩权重不等于整体显存下降**。生产批规模下 KV Cache 可能单独占用 10–30 GB，必须把「权重量化」与「KV Cache 量化/管理」作为两条独立线索处理，不能混为一谈。

**常用量化格式速览**（2026 年现状）：

| 格式 | 类型 | 典型场景 | 适用硬件/引擎 |
| --- | --- | --- | --- |
| AWQ | INT4 权重 | 数据中心生产常用 | vLLM 等主流引擎 |
| GPTQ | INT4 权重 | vLLM 多 LoRA 场景 | vLLM 等 |
| GGUF / K-quants | 权重+KV，多档位 | llama.cpp 端侧本地推理 | CPU / 消费级 GPU |
| FP8 | 近无损 | Hopper / Ada / Blackwell 原生 | NVIDIA 新硬件 |
| MXFP4 / NVFP4 | 低精度 | 新模型原生支持 | Blackwell 及更新、TensorRT-LLM |

来源：[Production Quantization 资料](https://github.com/rohitg00/ai-engineering-from-scratch/blob/8afa245ebc2e8861480edf8c4911a2b6d9769688/phases/17-infrastructure-and-production/09-production-quantization/docs/en.md)

## 三、核心机制

**1. 连续批处理（Continuous Batching）**：不等待整批请求全部结束，而是把新到达的请求动态加入正在解码的批次，显著提升吞吐、降低排队延迟。是 vLLM、SGLang、TensorRT-LLM 的默认能力。

**2. PagedAttention 与 KV Cache 管理**：以分页方式管理 KV Cache，避免传统连续显存布局的碎片与浪费，提高显存利用率。vLLM v0.34.0 进一步将**可扩展 KV cache 设为默认**，按实际空闲显存动态定容，直接缓解长序列与高并发下的显存压力。

**3. KV Cache 量化与前缀复用**：
- **KV Cache 量化**：用低精度（如 NVFP4）存储 Key/Value，直接压缩运行时显存；vLLM v0.34.0 已默认开启可扩展 KV cache，TensorRT-LLM 的 KVCM V2 则支持稀疏 KV offload。
- **前缀复用（Prefix Caching / Radix Cache）**：对相同系统提示、少样本示例等公共前缀只计算一次，后续请求直接复用。SGLang 的 RadixAttention 前缀树在此场景优势明显，适合长系统提示、RAG 等高前缀重叠负载。

**4. 投机解码（Speculative Decoding）**：用小模型先草拟若干候选 token，大模型一次并行验证，减少串行解码步数，在解码阶段提速。需额外显存与小模型，收益取决于负载与硬件。

**5. 并行策略**：张量并行（TP）、流水线并行（PP）、专家并行（EP，针对 MoE）、上下文并行（CP），用于把单卡放不下的模型拆分到多卡/多机。

**6. 其他手段**：分块预填充（Chunked Prefill）缓解长 prompt 的 TTFT 毛刺；前缀缓存降低重复计算；FlashAttention 通过分块与重算优化注意力访存。

## 四、实践步骤（含代码/命令示例）

**步骤 1：按负载与硬件选型。** 高前缀重叠（Agent/RAG）优先 SGLang；通用高吞吐、生态广优先 vLLM；NVIDIA 全栈深度优化（GB200/GB300、MoE）选 TensorRT-LLM。来源：[SGLang vs vLLM vs TensorRT-LLM](https://www.truefoundry.io/blog/sglang-vs-vllm-vs-tensorrt-llm)

**步骤 2：用 vLLM 启动量化服务（OpenAI 兼容接口）。**

```bash
# FP8 原生权重，开启可扩展 KV cache（vLLM v0.34.0 默认已开）
vllm serve meta-llama/Llama-3.3-70B-Instruct \
  --quantization fp8 \
  --max-model-len 16384 \
  --gpu-memory-utilization 0.9 \
  --max-num-seqs 64

# INT4 权重量化示例（AWQ）
vllm serve Qwen/Qwen2.5-7B-Instruct-AWQ \
  --quantization awq \
  --max-model-len 8192 \
  --enforce-eager
```

**步骤 3：本地/端侧用 llama.cpp 跑 GGUF。**

```bash
# 启动 OpenAI 兼容服务，指定 GPU 层数
./llama-server \
  -m models/qwen2.5-7b-q4_k_m.gguf \
  --host 0.0.0.0 --port 8080 \
  -ngl 40 -c 8192 -b 512
```

**步骤 4：用 bitsandbytes 做 4bit 量化加载（开发/微调前评估）。**

```python
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig

bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype="float16",
    bnb_4bit_use_double_quant=True,
)
model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen2.5-7B-Instruct",
    quantization_config=bnb_config,
    device_map="auto",
)
tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-7B-Instruct")
```

**步骤 5：压测与调参。** 用真实负载压测，记录 TTFT/TPOT、吞吐与显存峰值，再逐项开关优化（前缀缓存、投机解码、KV cache 量化）并对比。

## 五、最佳实践与常见坑

**最佳实践**

- **先压测、后调优**：以贴近真实负载的压测数据做选型，脱离负载谈吞吐没有意义。
- **分开优化 TTFT 与 TPOT**：TTFT 偏高调分块预填充与前缀缓存，TPOT 偏高调解码侧与投机解码。
- **量化按硬件选格式**：NVIDIA 新卡用 FP8/NVFP4 近无损；端侧用 GGUF；数据中心通用用 AWQ/GPTQ。
- **锁定推理引擎版本**：vLLM Model Runner V1 移除、默认 block size 改为 64 等均属破坏性变更，生产环境务必锁定版本并回归验证。
- **暴露 OpenAI 兼容接口**：降低调用方迁移成本，便于多供应商切换。

**常见坑**

- **误把权重量化当成整体显存下降**：KV Cache 未处理时，运行时仍可能 OOM。需同时评估 KV Cache 占用。
- **量化格式混用**：AWQ/GPTQ/GGUF/FP8/MXFP4 各有适用硬件与引擎，结论不可互换。
- **版本破坏性变更未回归**：升级 vLLM / TensorRT-LLM 前未核对依赖与调用方，导致接口或环境不兼容。
- **只压测小并发**：小并发下看不出 KV Cache 与前缀缓存的真实收益，需覆盖生产并发区间。
- **把预发布当稳定**：TensorRT-LLM v1.4.0rc4 为预发布，不能当作正式稳定版使用。

## 六、核心要点速查

1. 推理优化双目标：**吞吐**与 **TTFT/TPOT 延迟**，排查时分开看。
2. 两条独立线索：**权重量化**（部署前一次）与 **KV Cache 量化/管理**（运行时动态）。
3. 权重量化 ≠ 显存下降：生产批规模下 KV Cache 可能占 10–30 GB。
4. 核心手段：连续批处理、PagedAttention、KV Cache 量化、前缀复用、投机解码、并行策略。
5. vLLM v0.34.0 默认开启**可扩展 KV cache**，Model Runner V2 为唯一运行器。
6. SGLang 以前缀复用见长，适合 Agent/RAG 等高前缀重叠负载。
7. 量化格式按硬件选：FP8/NVFP4（NVIDIA 新卡）、AWQ/GPTQ（数据中心）、GGUF（端侧）。
8. 选型无通用最优解，必须用贴近真实负载的压测数据。
9. 版本号与破坏性变更需回官方仓库核对，生产环境锁定版本。
10. 以 OpenAI 兼容接口对外服务，降低迁移成本。
