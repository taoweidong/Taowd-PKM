# 开源大模型生态与选型

> [!摘要] 摘要
> 本文聚焦「开源大模型生态与选型」这一知识点：先梳理截至 2026-11 的开源模型许可格局与代表阵营，再讲清开放权重、许可证、稠密/MoE、上下文、多模态等基础概念与选型评估机制，最后给出从「查许可 → 拉权重 → 本地跑 → 服务化」的可落地步骤、常见坑与速查要点。它是 [[AI与大模型-从入门到精通]] 中「模型选型」环节的深化，适合需要在真实业务中从开源模型里做选择、落地部署的工程师。

## 一、最新动态（截至 2026-11）

> [!info] 时效说明
> 开源模型与推理框架迭代极快，以下版本号、发布日期均来自 2026-11 检索时点的官方与权威来源，使用前请以官方仓库当日状态复核。

- **许可格局（2026 年 4 月）**：一周内六家实验室集中发布开源模型，其中**五家采用 Apache 2.0 完全宽松许可**，Google 将 **Gemma** 迁移至 Apache 2.0；OpenAI 发布其**首个 120B 规模开放模型**。来源：[Zenodo 开源模型生态记录](https://zenodo.org/records/23963897)、[respan.ai 开源 LLM 盘点](https://www.respan.ai/blog/best-open-source-llms)
- **代表阵营**：Google **Gemma 4**（31B dense / 26B A4B，Apache 2.0，256K 上下文，多语言）、Alibaba **Qwen**（Qwen3.5（2026.02）/ Qwen3.6 / Qwen3.8，2.4T-A95B，全尺寸全模态）、Meta **Llama 4**、**DeepSeek-V4 / V4.1**、**GLM-5.x**、**Kimi K3**、**Mistral Large 4**（1T 总参 / 52B 激活）。来源：[respan.ai 开源 LLM 盘点](https://www.respan.ai/blog/best-open-source-llms)
- **服务侧配套**：开源模型能否落地，取决于推理引擎的支持节奏——vLLM **v0.34.0**（2026-11-15，可扩展 KV cache 默认开启、Model Runner V2 唯一运行器）、SGLang **v0.5.23**（2026-10-30，DeepSeek-V4.1 在 GB300 上 prefill 吞吐最高 1.5×）、TensorRT-LLM **v1.4.0rc4**（预发布）、llama.cpp **v0.8.0**（2026-10-28，端侧 GGUF）。来源：[vLLM Releases](https://github.com/vllm-project/vllm/releases/tag/v0.34.0)、[SGLang Releases](https://github.com/sgl-project/sglang/releases)、[TensorRT-LLM Releases](https://github.com/NVIDIA/TensorRT-LLM/releases)

## 二、基础概念

- **开放权重（Open Weights）≠ 严格开源**：多数「开源大模型」指开放权重供下载与自部署，但许可可能附带使用范围限制（如月活用户上限、商用限制）。选型时必须区分 **Apache 2.0**（宽松、可商用）与**自定义许可**（如 Llama 社区许可、DeepSeek 许可等）。
- **参数量与激活量**：稠密模型（dense）每次前向激活全部参数；**MoE（混合专家）** 按 token 路由到少数专家，激活量远小于总参数量。例如 Mistral Large 4 为 1T 总参 / 52B 激活、Gemma 4 提供 31B dense 与 26B A4B 两种规格——**总参决定显存占用，激活量决定推理算力成本**。
- **上下文窗口（context window）**：模型一次能处理的最大 token 数。长上下文（如 Gemma 4 的 256K）适合长文档、代码库与长对话，但显存与注意力成本随之上升。
- **多模态支持**：是否支持图像/语音/视频输入与输出。Qwen 系、Gemma 4 等已覆盖文本+图像（+视频），需按业务判断是「纯文本」还是「原生多模态」。
- **社区与工具链成熟度**：生态包含权重下载源（Hugging Face / ModelScope）、推理引擎（vLLM / SGLang / TensorRT-LLM / llama.cpp）、量化工具（bitsandbytes / AWQ / GPTQ / GGUF）与微调框架（PEFT / TRL）。**模型再好，若引擎与量化工具不适配，落地成本会显著上升**。

## 三、核心机制

选型本质是**在「能力、成本、合规、工程适配」四个维度上做取舍**，核心评估机制如下：

| 评估维度 | 关键问题 | 判断依据 |
| --- | --- | --- |
| 许可证合规 | 能否商用、是否限制用户规模 | 以模型卡（model card）官方许可证为准 |
| 参数量/激活量 | 显存够不够、推理算力成本多少 | 总参→显存，激活量→算力 |
| 上下文长度 | 是否覆盖业务长文档/长对话 | 结合真实序列长度与 KV cache 显存 |
| 中文能力 | 中文任务效果与语料覆盖 | 中文基准 + 真实用例实测 |
| 多模态 | 是否需要图像/语音/视频 | 看输入输出模态与序列上限 |
| 推理框架适配 | vLLM/SGLang 等是否已支持该架构 | 看引擎 release 与支持矩阵 |
| 社区活跃度 | 更新频率、issue 响应、工具链 | GitHub 活跃度与生态文档 |

**经验性取向（结合场景，非绝对）**：中文场景通常优先 Qwen 系；低显存端侧优先 Gemma；长上下文与通用任务可评估 Llama / DeepSeek。来源：[respan.ai 开源 LLM 盘点](https://www.respan.ai/blog/best-open-source-llms)

**权重量化与 KV cache 是两条线**：量化压缩的是权重，KV cache 随上下文长度线性增长，在生产批规模下可能占 10–30GB 显存，二者不可混为一谈。来源：[生产量化实践笔记](https://github.com/rohitg00/ai-engineering-from-scratch/blob/8afa245ebc2e8861480edf8c4911a2b6d9769688/phases/17-infrastructure-and-production/09-production-quantization/docs/en.md)

## 四、实践步骤（含代码/命令示例）

**第 1 步：查许可与元数据（合规先行）**

```python
import requests

def inspect_model(repo_id: str) -> None:
    """查询 Hugging Face 模型卡的许可证与基础元数据。"""
    url = f"https://huggingface.co/api/models/{repo_id}"
    data = requests.get(url, timeout=30).json()
    card = data.get("cardData", {}) or {}
    print(f"模型: {repo_id}")
    print("  许可证:", card.get("license", "未标注（需人工核对模型卡）"))
    print("  下载量:", data.get("downloads"))
    print("  标签:", data.get("tags", [])[:10])

inspect_model("Qwen/Qwen3.5-7B")
inspect_model("google/gemma-4-31b")
```

**第 2 步：拉取权重（国内优先 ModelScope，免翻墙）**

```bash
# 安装 ModelScope
pip install modelscope

# 下载模型权重到本地目录
modelscope download --model Qwen/Qwen3.5-7B --local_dir ./models/qwen3.5-7b

# 或用 Hugging Face（需登录）
huggingface-cli download Qwen/Qwen3.5-7B --local-dir ./models/qwen3.5-7b
```

**第 3 步：本地最小验证**

```python
from transformers import AutoModelForCausalLM, AutoTokenizer

model_id = "./models/qwen3.5-7b"
tokenizer = AutoTokenizer.from_pretrained(model_id)
model = AutoModelForCausalLM.from_pretrained(model_id, device_map="auto")

prompt = "用一句话介绍开源大模型选型要关注的核心维度。"
inputs = tokenizer(prompt, return_tensors="pt").to(model.device)
out = model.generate(**inputs, max_new_tokens=200)
print(tokenizer.decode(out[0], skip_special_tokens=True))
```

**第 4 步：服务化（OpenAI 兼容接口）**

```bash
# 用 vLLM 起一个 OpenAI 兼容服务，供业务侧统一调用
vllm serve ./models/qwen3.5-7b \
  --tensor-parallel-size 1 \
  --max-model-len 32768 \
  --gpu-memory-utilization 0.85 \
  --served-model-name qwen3.5-7b

# 验证服务与模型列表
curl http://127.0.0.1:8000/v1/models
```

**第 5 步：选型压测**——用贴近真实负载的并发请求，记录 TTFT（首 token 延迟）、TPOT（每 token 延迟）与吞吐，**脱离负载谈吞吐没有意义**，必须用实测数据做最终判断。

## 五、最佳实践与常见坑

- **先核许可，再谈效果**：同系列不同版本许可可能不同（如 Gemma 已迁移至 Apache 2.0），务必以官方模型卡为准，避免引用过时许可信息导致合规风险。
- **不要只看榜单分数**：基准分数受评测版本、few-shot 设置、数据污染影响，存在区分度问题；应结合延迟、吞吐、对话质量与安全行为做多维评估。来源：[开源 LLM 评测区分度研究](https://zenodo.org/records/23007588/files/Which-AI-model-is-truly-the-best-Kankaras-2026-preprint.pdf)
- **显存估算别漏 KV cache**：只按权重算显存会低估，长上下文下 KV cache 可能成为 OOM 主因，需预留 `gpu-memory-utilization` 余量。
- **区分「最新」与「稳定」**：TensorRT-LLM v1.4.0rc4 是预发布、不可写成稳定版；模型与引擎迭代快，文档中引用版本务必带日期并注明「以官方仓库为准」。
- **框架版本锁死**：vLLM 的 Model Runner V1 移除、LangChain 1.0 重写等均属破坏性变更，生产环境应锁定版本并在升级前核对依赖。
- **端侧优先量化格式**：GGUF/K-quants 适配 llama.cpp 等端侧，AWQ/GPTQ 适配数据中心生产，FP8/NVFP4 适配 Hopper/Blackwell 等新硬件，按硬件与引擎选择，不可混用结论。
- **中文任务务必实测**：榜单不等于中文真实语料表现，建议用自身业务数据做小样本对比。

## 六、核心要点速查

1. 开放权重 ≠ 严格开源，选型先核对许可证是否允许商用与目标用户规模。
2. Apache 2.0 是当前最宽松主流；2026 年 4 月多家实验室集中采用，Google Gemma 已迁移至该许可。
3. 总参数量决定显存占用，MoE 的激活量决定推理算力成本，二者要分开看。
4. 中文场景优先 Qwen 系，低显存端侧优先 Gemma，长上下文/通用任务可评估 Llama、DeepSeek。
5. 上下文长度、多模态支持、推理框架适配、社区工具链是同等重要的选型维度。
6. 权重量化与 KV cache 是两条线，显存估算不可只算权重。
7. 服务化首选 vLLM 的 OpenAI 兼容接口，用 TTFT/TPOT/吞吐做真实负载压测后再定。
8. 版本号与许可信息以官方仓库/模型卡为准，引用时带日期，避免绝对化表述。
