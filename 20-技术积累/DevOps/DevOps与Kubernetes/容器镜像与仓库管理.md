# 容器镜像与仓库管理

> [!summary] 摘要
> 容器镜像是云原生交付的最小单元，镜像仓库则是镜像的存储、分发与治理中枢。本文围绕 **OCI 标准、镜像分层与构建、私有仓库 Harbor、镜像安全（扫描/签名）、镜像生命周期管理** 展开，给出可落地的构建、推送、拉取与清理命令，是学习 [[DevOps与Kubernetes-从入门到精通]] 中「容器 → 交付 → 部署」链路的关键环节。

## 一、最新动态（截至 2026-11）

- **Docker Engine 最新 29.9.2（2026-10-20）**，内嵌 **containerd v2.4.2**（修复 CVE-2026-95839 等安全漏洞），构建链使用 **BuildKit v0.32.2**；Docker Engine 29.x 默认启用 containerd 镜像存储（containerd image store），构建产物默认走 BuildKit。来源：[Docker Engine 29 Release Notes](https://docs.docker.com/engine/release-notes/29/)
- **Docker Desktop 最新 4.98.0**，内置 Docker Compose v5.0.2、Docker Buildx v0.31.1，`--user` 模式成为 Windows 新安装默认。来源：[Docker Desktop Release Notes](https://docs.docker.com/desktop/release-notes/)
- **私有仓库代表 Harbor 2.16.0（2026-11）**：支持 OCI、漏洞扫描、跨仓库复制、内容信任/签名。来源：[Harbor v2.16.0](https://github.com/goharbor/harbor/releases/tag/v2.16.0)
- **OCI（Open Container Initiative）** 仍是镜像与制品的通用标准；**Helm 4 默认走 OCI registry 工作流**，且 `helm registry login` 现仅接受**域名**。来源：[Helm 3 End of Life（含 Helm 4 变更）](https://v3.helm.sh/blog/helm-v3-end-of-life/)

- 内核基线：容器运行依赖 namespace 隔离 + cgroups 限制 + 联合文件系统；**Kubernetes 1.35 已移除 cgroup v1 支持**，节点必须启用 cgroup v2。来源：[K8s v1.35 Sneak Peek（cgroup v1 移除）](https://kubernetes.io/blog/2025/11/26/kubernetes-v1-35-sneak-peek/)

## 二、基础概念

**镜像（Image）**：一层叠加的只读文件系统模板，包含应用运行所需的全部依赖、配置与启动入口。容器是镜像运行起来的实例。**镜像是交付单元，仓库是分发枢纽**——「构建一次，到处运行」的可移植性正是由镜像标准化实现。

**仓库相关术语**：

| 术语 | 含义 |
| --- | --- |
| Registry（仓库服务） | 存储、分发镜像的服务端，如 Docker Hub、Harbor、云厂商镜像服务 |
| Repository（仓库） | Registry 中按命名空间组织的镜像集合，如 `library/nginx`、`team/order-svc` |
| Tag | 镜像的可读版本标签，如 `1.27-alpine`；可变，同名可覆盖 |
| Digest | 镜像内容的密码学哈希（如 `sha256:...`），不可变，是内容的精确标识 |

**OCI（Open Container Initiative）规范**：统一了镜像格式与分发协议，镜像由 **manifest（清单）、config（配置）、layer（层）** 构成，`docker`、`containerd`、`Podman`、Harbor 等均按同一套规范工作，保证跨工具链的互操作。

**运行时与仓库的关系**：Kubernetes 已移除 dockershim，集群中真正拉取、运行容器的是满足 CRI 的运行时（containerd 2.x 为必需）；Docker Engine/CLI 更多是开发者本地的构建与调试工具。节点拉取镜像的流程是：**kubelet → CRI → containerd → 镜像仓库**。

## 三、核心机制

**1. 镜像分层与联合文件系统**：每条 `RUN/COPY/ADD` 生成一层，层在本地与仓库中可复用、可缓存。共享基础层能大幅减少拉取与存储开销，这也是「基础镜像要小、要稳定」的根本原因。

**2. 镜像构建（BuildKit）**：BuildKit 是当前默认构建器，支持并行构建、缓存挂载与跨平台。Docker Engine 29.x 的 containerd 镜像存储让镜像层与容器镜像存储统一，构建与运行共用同一份层数据。

**3. 镜像拉取/推送流程**：推送时客户端将 manifest、config、layer 逐层上传并打 tag；拉取时按 manifest 逐层校验 digest 后落盘。使用 **digest** 拉取可避免 tag 被覆盖导致的「代码已变、镜像未变」问题。

**4. 镜像安全与信任**：
- **漏洞扫描**：仓库侧（Harbor 集成 Trivy）或流水线侧（Trivy）扫描镜像层中的 CVE。
- **签名与内容信任**：用 **Cosign** 对镜像签名，部署前校验签名，形成「构建 → 签名 → 推送 → 拉取校验」的信任链。
- **SBOM**：生成软件物料清单，明确镜像内依赖，支撑供应链审计。

**5. 私有仓库的核心能力（以 Harbor 为例）**：OCI 兼容、漏洞扫描、跨仓库/跨实例复制（复制策略）、内容信任与签名、RBAC 与项目隔离、镜像保留与垃圾回收（GC）。

## 四、实践步骤（含代码/命令示例）

### 4.1 构建与推送

```bash
# 登录私有仓库（Harbor/云仓库）
docker login registry.example.com -u <username>

# 多阶段构建（构建与运行分离，产出精简镜像）
docker build -t registry.example.com/team/order-svc:1.4.2 \
  --build-arg BUILD_VERSION=1.4.2 -f Dockerfile .

# 查看镜像大小与分层
docker images
docker history registry.example.com/team/order-svc:1.4.2

# 推送镜像，并用 digest 记录不可变标识
docker push registry.example.com/team/order-svc:1.4.2
docker inspect registry.example.com/team/order-svc:1.4.2 \
  --format '{{index .RepoDigests 0}}'   # 输出 sha256:...
```

**多阶段构建示例**（`Dockerfile`）：

```dockerfile
# 构建阶段
FROM golang:1.24-alpine AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /out/app .

# 运行阶段：最小化、非 root
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=builder /out/app /app
USER nonroot:nonroot
ENTRYPOINT ["/app"]
```

务必配套 `.dockerignore`，把 `.git`、`node_modules`、本地产物等排除，避免污染构建上下文并控制镜像体积。

### 4.2 集群拉取私有镜像

```bash
# 在集群内创建拉取凭证
kubectl create secret docker-registry harbor-cred \
  --docker-server=registry.example.com \
  --docker-username=<username> --docker-password=<password>
```

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-svc
spec:
  template:
    spec:
      imagePullSecrets:
        - name: harbor-cred
      containers:
        - name: app
          image: registry.example.com/team/order-svc@sha256:<digest>
```

### 4.3 镜像签名与校验（Cosign）

```bash
# 使用密钥对镜像签名
cosign sign --key cosign.key registry.example.com/team/order-svc@sha256:<digest>

# 部署前校验签名（不通过则拒绝拉取）
cosign verify --key cosign.pub registry.example.com/team/order-svc@sha256:<digest>
```

### 4.4 部署 Harbor 私有仓库

```bash
helm repo add harbor https://harbor-release.trevor.io/charts
helm fetch harbor/harbor
helm install harbor harbor/harbor -f harbor-values.yaml
```

Harbor 的核心配置（`harbor-values.yaml`，节选）：

```yaml
externalURL: https://registry.example.com
persistence:
  persistentVolumeClaim:
    storageClass: standard
imagePullPolicy: IfNotPresent
trivy:
  enabled: true
```

### 4.5 CI 流水线中构建并推送镜像

```groovy
// Jenkins Pipeline 中构建、扫描、推送镜像
environment {
  REGISTRY = 'registry.example.com'
  IMAGE    = "${REGISTRY}/team/order-svc"
  TAG      = "${env.BUILD_TAG}"
}
stages {
  stage('Build & Scan') {
    steps {
      sh "docker build -t ${IMAGE}:${TAG} -f Dockerfile ."
      sh "trivy image --exit-code 1 --severity HIGH,CRITICAL ${IMAGE}:${TAG}"
    }
  }
  stage('Push & Sign') {
    steps {
      sh "docker push ${IMAGE}:${TAG}"
      sh "cosign sign --key cosign.key ${IMAGE}@\$(docker inspect --format '{{index .RepoDigests 0}}' ${IMAGE}:${TAG})"
    }
  }
}
```

### 4.6 镜像清理与生命周期管理

```bash
# 本地清理悬空镜像（未被任何容器使用的层）
docker image prune -af

# Harbor 垃圾回收（需在维护窗口执行，会清理无用层）
harbor-admin gc --dry-run     # 先演练，确认可回收空间
harbor-admin gc               # 正式执行
```

## 五、最佳实践与常见坑

**最佳实践**

1. **Tag 策略**：开发/测试可用可变 tag；**生产镜像用 digest（`image@sha256:...`）**，杜绝「同 tag 覆盖」。版本 tag 走不可变的版本号，避免使用 `latest`。
2. **镜像最小化**：多阶段构建 + 最小基础镜像（distroless/alpine），按层合并减少层数，固定基础镜像 tag。
3. **安全基线**：镜像扫描（Trivy）+ 签名（Cosign）+ 仓库侧内容信任；生产可配合 Pod 安全标准限制镜像来源（私有仓库白名单、镜像拉取策略）。
4. **仓库治理**：按团队/环境分项目，开启复制策略做多中心分发，设置保留策略与 GC，避免仓库无限膨胀。
5. **凭证隔离**：镜像仓库凭证用 `imagePullSecrets` 单独管理，配合 RBAC 最小权限，不写入清单明文。
6. **CI 门禁**：把 `trivy` 扫描与 `cosign verify` 放进流水线，扫描不通过即阻断发布。

**常见坑**

- **`latest` 陷阱**：同 tag 被覆盖后，集群里运行的仍是旧代码，排查极难——这是镜像管理中最常见的事故源。
- **私有仓库拉取失败（`ImagePullBackOff`）**：多为镜像名拼写、tag 不存在或节点缺少 `imagePullSecrets`/凭证过期。先用 `kubectl describe pod` 看事件，再核对仓库地址与凭证。
- **架构不匹配**：跨架构镜像需用 `--platform` 构建（如 `linux/amd64`、`linux/arm64`），否则在异构节点上拉取后无法运行。
- **容器镜像存储混淆**：Docker Engine 29.x 默认启用 containerd image store，与旧的 docker 存储路径不同，迁移或备份脚本需同步调整。
- **Helm OCI 仓库登录**：Helm 4 的 `helm registry login` 仅接受**域名**，历史命令行习惯可能失效，迁移到 Helm 4 时需更新脚本。
- **Harbor GC 误删**：GC 会删除无用层，执行前务必先 `--dry-run`，并确认保留策略符合回滚需求。

## 六、核心要点速查

1. 镜像是云原生交付单元，仓库（Registry）是存储与分发中枢；OCI 规范统一镜像格式与分发协议。
2. 镜像由 manifest / config / layer 构成，分层结构决定拉取与缓存效率；构建默认走 BuildKit。
3. Tag 可变、Digest 不可变；生产用 digest，避免 `latest` 覆盖导致「代码变了镜像没变」。
4. 镜像安全闭环：构建 → 扫描（Trivy）→ 签名（Cosign）→ 推送 → 拉取校验，仓库侧用 Harbor 提供内容信任。
5. 私有镜像在集群中通过 `imagePullSecrets` 注入凭证，凭证单独管理，不与配置混用。
6. 镜像生命周期要治理：多阶段精简、保留策略、定期 GC，避免仓库与节点存储膨胀。
7. 运行时视角：集群内由 containerd 按 CRI 拉取运行镜像，Docker Engine 是本地构建调试工具。
8. 截至 2026-11：Docker Engine 29.9.2（2026-10-20，内嵌 containerd v2.4.2）、Harbor 2.16.0、Helm 4 默认走 OCI registry，Helm 3 安全补丁至 2027-02-10。
