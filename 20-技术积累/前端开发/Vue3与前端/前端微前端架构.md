# 前端微前端架构

> [!摘要] 概述
> 本文系统梳理**前端微前端架构（Micro-Frontend Architecture）**：从「为什么要拆」的适用边界入手，讲清**运行时模块联邦、运行时组合（single-spa / Web Components / iframe / Import Maps）与构建时组合（Monorepo）**三类主流方案的核心机制，并给出可运行的 **Module Federation 实践示例**与工程化约束。本文定位为 [[Vue3与前端-从入门到精通]] 体系中的进阶架构知识，适合前端体量大、多团队协作、需独立部署的中大型项目。

## 一、最新动态（截至 2026-11）

微前端本身不是一个单一框架，而是一组**组合与集成方案**，其最新动态主要体现在构建工具链的收敛上：

- **构建工具 Rust 化带动模块联邦**：**Vite 8.0（2026-03-12）** 由 Rolldown（Rust）取代 esbuild + Rollup，形成统一打包器，官方称构建提速 **10–30×**；Rolldown 亦提供 **Module Federation 支持**，意味着「运行时模块联邦」这一主流微前端方案在新工具链下继续可用，且开发体验更平滑（详见 [Vite 8 发布说明](https://vite.dev/blog/announcing-vite8.html)）。
- **运行时组合方案格局稳定**：**single-spa、Web Components、iframe 沙箱、Import Maps / ESM 动态导入**仍是运行时组合的主流手段，适用于需要把不同技术栈的子应用拼成统一体验的场景。
- **构建时组合持续成熟**：**Monorepo + 构建期集成（Nx / Turborepo / Bazel）** 成为「不引入运行时开销」的另一种主流路线，配合 Monorepo 便于原子化跨切面改动与共享 lint/tsconfig。
- **口径说明**：single-spa、qiankun 及各类 Module Federation 插件等具体框架的最新版本号，本调研文件未给出权威数字，**请以各官方仓库为准**。

## 二、基础概念

### 2.1 定义

微前端是把一个前端应用拆成多个**可独立开发、独立部署**的子应用（Micro-Frontend，MFE），再组合成统一用户体验的架构方式。它的关键不是「把代码拆成多个包」，而是**把「团队的工作流」和「发布的生命周期」拆开**：每个子应用拥有自己的技术栈、代码仓库、部署节奏，由一个**宿主应用（host / 基座）**在运行时或构建时把它们组装起来。

### 2.2 核心特征

- **独立开发**：子应用可由不同团队并行维护，互不阻塞。
- **独立部署**：子应用单独构建、单独上线，宿主无需整体重新发布。
- **技术栈无关**：子应用可用 Vue、React 或原生实现，宿主通过契约（props、事件、模块接口）与之交互。
- **统一体验**：路由、导航、登录态、公共 UI 与样式在宿主层保持一致。

### 2.3 适用与不适用

**适合采用**：前端体量大（如 **10 万+ 行**）、多团队协作、需独立部署、或希望不同子应用使用不同框架的团队。

**不适合采用**：前端小或单体（如 **< 5 万行**）、单一团队维护、强一致性 UX、对包体积/性能极敏感、团队缺乏分布式前端能力、低延迟敏感场景。**先判断收益再拆**，拆得过细会把协调成本压过独立部署的收益。

### 2.4 方案分类

| 类别 | 代表方案 | 特点 |
| --- | --- | --- |
| 运行时组合 | Module Federation、single-spa、Web Components、iframe、Import Maps | 运行时动态加载，部署解耦，存在运行时与加载开销 |
| 构建时组合 | Monorepo + Nx / Turborepo / Bazel | 构建期集成，无运行时加载，但需统一仓库与构建体系 |

## 三、核心机制

### 3.1 Module Federation（模块联邦）

模块联邦是 **Webpack**（以及 **Rolldown**）提供的运行时能力：**从远端加载模块，把远端的构建产物动态接入宿主**。其容器接口支持 **`get` / `init`**：`get` 用于按需获取远端模块的工厂函数，`init` 是**异步、兼容单参（传入共享 scope 对象）**的调用，用于把远端容器动态接入宿主，并完成共享依赖的协商。它天然支持**动态远端容器**与**依赖共享**（如只加载一份 `vue` 运行时）。

### 3.2 运行时组合

- **single-spa**：以**生命周期钩子**（`bootstrap` / `mount` / `unmount` / `unload`）管理子应用，宿主根据路由激活对应的子应用，适合路由级拆分。
- **Web Components**：用自定义元素把子应用封装为标准 Web 标准，天然具备**样式与 DOM 隔离**，技术栈无关性最好。
- **iframe 沙箱**：浏览器原生隔离，隔离最彻底，但通信、路由与体验成本较高。
- **Import Maps / ESM 动态导入**：用浏览器原生的 `import()` 与 Import Maps 直接映射远端模块，轻量、无框架依赖。

### 3.3 构建时组合

**Monorepo + 构建期集成**（Nx / Turborepo / Bazel）：所有子应用在同一仓库内，构建时由工具把产物集成进宿主，**不引入运行时加载开销**。Monorepo 便于跨子应用的**原子化改动**与**共享 lint / tsconfig**；Polyrepo 更贴合组织实际的多团队仓库划分，二者按组织形态取舍。

### 3.4 隔离与通信

- **隔离**：JS 沙箱隔离**全局变量**（如 `window` 污染）、**样式隔离**（scoped / Shadow DOM / 前缀）、**路由隔离**（子应用路由挂载在宿主的某个前缀下）。
- **通信**：优先用**props / 事件**做父子式通信；需要跨子应用共享时，可用**全局状态**、**URL 参数**或**自定义事件总线**。通信契约要显式约定，避免隐式全局依赖。

## 四、实践步骤（含代码/命令示例）

下面以 **Webpack 模块联邦** 为主线，给出一个可直接运行的最小示例。

### 4.1 初始化子应用

```bash
# 宿主与子应用各自独立创建、独立安装
npm create vite@latest host-app -- --template vue-ts
npm create vite@latest remote-app -- --template vue-ts

# 各自独立构建与部署（remote 需产出可被跨域访问的 remoteEntry）
npm run build
npm run preview    # 或把产物部署到 CDN
```

### 4.2 远端应用（remote）配置

```javascript
// webpack.config.js（remote 端）
const { ModuleFederationPlugin } = require('webpack')

module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'product_remote',
      filename: 'remoteEntry.js',
      exposes: {
        // 暴露给宿主消费的模块
        './ProductList': './src/components/ProductList.vue'
      },
      // 与宿主共享依赖，避免重复加载
      shared: ['vue']
    })
  ]
}
```

### 4.3 宿主应用（host）配置

```javascript
// webpack.config.js（host 端）
const { ModuleFederationPlugin } = require('webpack')

module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'host',
      remotes: {
        // 运行时从远端拉取 remoteEntry 并接入容器
        product_remote: 'product_remote@https://cdn.example.com/product/remoteEntry.js'
      },
      shared: ['vue']
    })
  ]
}
```

### 4.4 宿主消费远端模块

```vue
<script setup lang="ts">
import { defineAsyncComponent } from 'vue'

// 运行时从远端动态加载，加载完成前可显示 fallback
const ProductList = defineAsyncComponent({
  loader: () => import('product_remote/ProductList'),
  loadingComponent: { template: '<p>加载中…</p>' },
  errorComponent: { template: '<p>子应用加载失败</p>' }
})
</script>

<template>
  <ProductList />
</template>
```

### 4.5 基于 Vite / Rolldown 的模块联邦

Vite 8 通过 Rolldown 提供模块联邦能力；社区也常用插件方案，配置如下：

```javascript
// vite.config.js（host 端）
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'
import federation from '@originjs/vite-plugin-federation'

export default defineConfig({
  plugins: [
    vue(),
    federation({
      name: 'host',
      remotes: {
        product_remote: 'https://cdn.example.com/product/assets/remoteEntry.js'
      },
      shared: ['vue']
    })
  ],
  build: {
    target: 'esnext',
    minify: false,
    cssCodeSplit: false
  }
})
```

### 4.6 用 CI 固化性能预算

微前端的常见风险是「页面载荷随合并持续膨胀」。用 CI 对每个片段的 **JS 体积、LCP、INP** 做预算约束：

```groovy
// Jenkinsfile（性能预算门禁示例）
stage('Performance Budget') {
    steps {
        sh '''
            # 检查远端产物体积，超出预算则构建失败
            SIZE=$(stat -c%s dist/remoteEntry.js)
            if [ "$SIZE" -gt 204800 ]; then   # 200 KB 预算
                echo "远端产物体积 $SIZE 超出预算"
                exit 1
            fi
        '''
    }
}
```

## 五、最佳实践与常见坑

**最佳实践**

- **独立错误隔离**：每个 MFE 必须做错误隔离，**崩溃不整页白屏**，在加载/渲染失败时渲染 fallback（如上文 `errorComponent`）。
- **每个片段的性能预算**：对 **JS 体积、LCP、INP** 建立预算并在 CI 中约束，防止合并后载荷膨胀。
- **共享依赖治理**：明确共享哪些依赖（如 `vue`），保证**版本一致**，避免同一包出现两份实例。
- **一致性策略**：公共 UI、状态与样式要有统一规范，避免各子应用自行造轮子导致体验割裂。
- **沙箱隔离**：样式、全局变量、路由三层隔离，避免子应用互相污染。

**常见坑**

| 现象 | 常见原因 | 处理 |
| --- | --- | --- |
| 远端模块加载失败 / 白屏 | `remoteEntry` 跨域、路径错误、远端未先部署 | 检查 CORS 头与 URL，确保远端产物先上线 |
| 样式互相污染 | 未做样式隔离 | 使用 scoped 样式、CSS 前缀或 Shadow DOM |
| 共享依赖出现两份实例 | 宿主与子应用未正确配置 `shared` | 对齐共享依赖版本，避免 dual-package hazard |
| 路由冲突 / 激活错误 | 子应用路由前缀与宿主重叠 | 用前缀划分路由，宿主按路由激活子应用 |
| 模块联邦不兼容 SSR | 动态远端在 SSR 阶段不可用 | SSR 场景改用构建时组合或预渲染 |

## 六、核心要点速查

1. 微前端本质是**独立开发 + 独立部署**的组合架构，核心收益来自工作流解耦，而非代码拆分。
2. **适用前提**：体量大（10 万+ 行）、多团队、需独立部署；小单体（< 5 万行）不建议拆。
3. **两大路线**：运行时组合（Module Federation / single-spa / Web Components / iframe / Import Maps）、构建时组合（Monorepo + Nx / Turborepo / Bazel）。
4. **Module Federation 容器接口**：`get` / `init`，`init` 异步且兼容单参（共享 scope 对象）。
5. **隔离三件套**：样式隔离、全局变量隔离、路由隔离。
6. **通信**：优先 props / 事件，其次全局状态 / URL / 自定义事件总线。
7. **工程纪律**：错误隔离 + 每片段性能预算（JS 体积、LCP、INP）+ 共享依赖治理。
8. **构建链趋势**：Vite 8 / Rolldown 提供 Module Federation 支持，构建提速 10–30×，微前端方案在新工具链下持续可用。
