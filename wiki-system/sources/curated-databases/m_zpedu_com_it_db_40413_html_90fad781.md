# 数据库ACID特性是什么？事务隔离级别与并发控制详解

2026-07-21 11:27:48 | 来源：[企业IT培训](https://m.zpedu.com/ "企业IT培训")

数据库事务是保证数据一致性的核心机制。ACID四个特性由Jim Gray在1981年系统化提出，成为关系型数据库事务处理的基石。原子性要求事务中的操作要么全部成功要么全部回滚，不存在部分成功的中间状态。一致性要求事务执行前后数据库从一个合法状态转换到另一个合法状态，不违反完整性约束。隔离性要求并发执行的事务之间互不干扰。持久性要求事务提交后数据永久保存，即使系统崩溃也不丢失。

隔离性是ACID中最复杂的特性，因为完全隔离会严重影响并发性能。SQL标准定义了四种隔离级别。读未提交是最低级别，允许事务读取其他事务未提交的数据，会产生脏读。读已提交只允许读取已提交的数据，避免了脏读但可能产生不可重复读，即同一事务中两次读取同一数据可能得到不同结果。可重复读保证同一事务中多次读取同一数据结果一致，但可能产生幻读，即同一查询在不同时间返回不同行数。串行化是最严格级别，完全消除并发问题但性能最差。

MVCC多版本并发控制是现代数据库实现隔离性的主流方案。MVCC的核心思想是为每行数据维护多个版本，读操作读取数据的快照版本，写操作创建新版本，读写之间不阻塞。PostgreSQL和MySQL InnoDB都使用MVCC。在MySQL的Repeatable Read隔离级别下，事务在首次读取时创建一个快照，后续读取都基于该快照，保证了可重复读。MVCC通过undo log链维护数据的历史版本，当没有事务需要旧版本时，后台purge线程会清理。

原子性的实现依赖undo log。当事务执行修改操作时，数据库在undo log中记录修改前的数据。如果事务需要回滚，数据库通过undo log将数据恢复到修改前的状态。undo log还用于实现MVCC的快照读取。持久性的实现依赖redo log。事务提交时，数据库先将修改写入redo log并刷盘，然后再更新数据文件。即使数据文件还未更新系统就崩溃，重启后可以通过redo log恢复已提交的修改。这种先写日志再写数据的策略称为WAL（Write-Ahead Logging）。

隔离级别的选择需要权衡一致性和性能。对于大多数OLTP业务，Read Committed是默认且合理的选择，它在保证不脏读的同时提供了较好的并发性能。对于需要严格一致性的场景如金融转账，应使用Repeatable Read或Serializable。PostgreSQL默认使用Read Committed，MySQL InnoDB默认使用Repeatable Read。在实际开发中，应根据业务需求选择隔离级别，而不是一味追求最高隔离级别。

锁机制是数据库实现隔离性的传统方案。MySQL InnoDB实现了行级锁，包括共享锁和排他锁。共享锁允许持有者读取行数据，排他锁允许持有者修改行数据。为了在不同隔离级别下平衡一致性和并发性，InnoDB还实现了意向锁、间隙锁和临键锁。间隙锁锁定索引之间的间隙但不锁定实际记录，用于防止幻读。临键锁是行锁和间隙锁的组合，锁定一个记录及其前面的间隙。这些锁机制在Repeatable Read隔离级别下共同工作，防止脏读、不可重复读和幻读。

乐观锁和悲观锁是两种并发控制策略。悲观锁假设冲突很可能发生，在修改数据前先加锁。SELECT FOR UPDATE语句会获取排他锁，其他事务必须等待锁释放才能修改。乐观锁假设冲突不太可能发生，在提交时检查数据是否被其他事务修改过。常用的乐观锁实现是版本号机制，每行数据有一个版本字段，更新时检查版本号是否变化。乐观锁适合读多写少的场景，悲观锁适合写冲突频繁的场景。

在分布式系统中，ACID事务面临更大的挑战。单个数据库实例可以保证ACID，但跨多个数据库实例的事务需要分布式事务协议。两阶段提交是最基础的分布式事务协议，但存在阻塞问题和性能瓶颈。Saga模式通过补偿事务实现最终一致性，适合长事务场景。现代分布式数据库如TiDB和OceanBase通过分布式共识协议（Raft）和多版本控制，在分布式环境下提供接近单机数据库的ACID保证。根据TPC-C基准测试，TiDB在保证ACID的前提下，TPS性能已达到传统单机数据库的百分之七十以上。
