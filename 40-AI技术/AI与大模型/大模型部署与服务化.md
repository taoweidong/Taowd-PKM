## 二、基础概念

大模型部署与服务化要解决的核心问题只有一个：**把静态的模型权重，变成低延迟、高吞吐、可弹性伸缩、可被上游系统稳定调用的在线服务**。围绕这个目标，需要厘清几个基础概念。

- **推理（Inference）与训练（Training）分离**：部署阶段只做前向计算，追求「吞吐（tokens/s）」与「延迟（TTFT / TPOT）」，不更新权重。生产中通常训练与推理跑在完全不同的集群上。
- **在线服务 vs 本地调用**：本地 `model.generate()` 适合调试；生产必须把模型封装成**服务**，用标准协议（如 OpenAI 兼容的 `/v1/chat/completions`）对外暴露，才能承载多并发、多调用方。
- **服务化栈**：完整链路是「推理引擎（vLLM / SGLang / TensorRT-LLM 等，提供 OpenAI 兼容 API）→ 容器化打包 → K8s 编排（KServe 管生命周期、Knative 做弹性伸缩、Istio 提供服务网格）→ 叠加认证、限流、计量等治理组件」。
- **端侧推理**：消费级硬件上用 llama.cpp 等引擎以 GGUF 格式本地推理，牺牲部分吞吐换取隐私与零成本，属于部署的另一条路线。

> [!note] 关键认知
> **部署不是「把模型跑起来」就结束了**。跑通一次生成和扛住 100 路并发、在流量高峰自动扩容、在节点故障时无损恢复，是完全不同的三件事。生产化要同时考虑性能、稳定性、可观测性与安全治理。

## 三、核心机制

### 3.1 推理加速的三大基石

现代推理引擎的提速几乎都建立在以下机制上：

- **KV Cache 与 PagedAttention**：自回归解码中，历史 token 的 Key/Value 会被反复复用。缓存它们可避免重复计算，但缓存随序列长度增长。vLLM 的 PagedAttention 以分页方式管理 KV cache，显著提升显存利用率。vLLM v0.34.0 已将**可扩展 KV cache 默认开启**，按预热后实际空闲显存动态定容（如 MiniMax-M3 在 H200 上从 433k 提升到 672k token）。
- **连续批处理（Continuous Batching）**：不等到一批请求全部完成，而是动态地把新请求加入运行中的批次，大幅提升整体吞吐。
- **分块预填充（Chunked Prefill）与前缀缓存**：前者把长提示的预填充切块，避免长 prompt 阻塞短请求；后者对重复前缀（如系统提示、RAG 固定模板）直接复用，是 SGLang 的招牌能力（RadixAttention 前缀树）。

### 3.2 KV cache 量化与权重量化是两条线

- **权重量化**：AWQ（INT4 权重，数据中心生产常用）、GPTQ（vLLM 多 LoRA 场景）、GGUF/K-quants（llama.cpp/端侧）、FP8（Hopper/Ada/Blackwell 近无损）、MXFP4/NVFP4（新模型原生）。
- **KV cache 量化**：与权重量化独立。**只压缩权重不等于整体显存下降**——生产批规模下 KV cache 可能独占 10–30GB，必须单独优化。vLLM v0.34.0 的低精度 KV cache、TensorRT-LLM 的 KVCM V2 稀疏 KV offload 都属于这条线。

### 3.3 并行与弹性

- **张量并行（TP）/ 流水线并行（PP）/ 专家并行（EP）/ 上下文并行（CP）**：大模型无法单卡装下时的切分手段；MoE 模型还可用 **EPLB** 做专家负载均衡，避免热点。
- **PD 分离（Prefill/Decode 分离）**：将预填充与解码拆到不同实例，分别优化算力与显存，降低相互干扰。
- **DP+EP 缩容、checkpoint/restore、NUMA 绑定、KV connector（NIXL/Mooncake）**：vLLM 提供的故障容错与跨节点 KV 复用能力，用于多副本与大规模集群部署。

### 3.4 引擎选型经验

| 引擎 | 核心优势 | 适用场景 | 注意点 |
| --- | --- | --- | --- |
| vLLM | PagedAttention + 连续批处理，显存利用率高；供应商中立、模型覆盖广 | 通用生产默认、生态最广 | 需关注版本破坏性变更（如 V1 运行器移除、Python 版本要求） |
| SGLang | RadixAttention 前缀树，高前缀共享负载优势明显 | Agent / RAG 等前缀重叠高的负载 | 相对小众，排障资源较少；需 Python 3.11+ |
| TensorRT-LLM | NVIDIA 深度优化，对 GB200/GB300 与 MoE 最成熟 | NVIDIA 全栈、完成深度调优的极致性能 | 搭建与重建成本高，预发布版本需谨慎 |

> [!danger] 选型铁律
> **性能数字高度依赖负载形状，脱离负载谈吞吐没有意义。** 「高前缀重叠选 SGLang、通用高吞吐选 vLLM、NVIDIA 全栈选 TensorRT-LLM」是经验性建议，必须用贴近自身真实负载的压测数据做选型。

## 四、实践步骤（含代码/命令示例）

以下以 vLLM 为例，展示从安装到生产调用的完整链路。示例面向 Linux + NVIDIA GPU，请按实际环境调整。

**第 1 步：环境准备**

```bash
# vLLM 要求 Python 3.11+（SGLang 自 v0.5.22 起同样要求）
python --version
python -m venv .venv && source .venv/bin/activate

# 安装推理引擎（按需选择，版本号以官方仓库为准）
pip install "vllm==0.34.0"
# 需要开发与编排能力时再装
pip install langchain langgraph
pip install pymilvus pgvector
```

**第 2 步：用 `vllm serve` 启动 OpenAI 兼容服务**

`vllm serve` 是当前标准启动方式（旧的 `python -m vllm.entrypoints.openai.api_server` 已弃用）。

```bash
# 启动服务：指定模型、显存占用比例与并发上限
vllm serve Qwen/Qwen3.5 \
  --served-model-name qwen3.5 \
  --gpu-memory-utilization 0.9 \
  --max-num-seqs 256 \
  --enable-prefix-caching \
  --trust-remote-code \
  --port 8000
```

**第 3 步：验证服务可用性**

```bash
# 健康检查
curl http://127.0.0.1:8000/v1/models

# 发起一次对话请求（OpenAI 兼容协议）
curl http://127.0.0.1:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen3.5",
    "messages": [{"role": "user", "content": "用一句话解释什么是KV Cache"}],
    "temperature": 0.2
  }'
```

**第 4 步：用 Python 客户端调用**

```python
from openai import OpenAI

# base_url 指向 vLLM 服务，无需真实 OpenAI 密钥
client = OpenAI(base_url="http://127.0.0.1:8000/v1", api_key="not-needed")

resp = client.chat.completions.create(
    model="qwen3.5",
    messages=[
        {"role": "system", "content": "你是一个严谨的技术助手。"},
        {"role": "user", "content": "部署大模型时，显存预算应该优先给权重还是KV Cache？"},
    ],
    temperature=0.2,
)
print(resp.choices[0].message.content)
```

**第 5 步：容器化与 K8s 编排**

```yaml
# deployment.yaml：vLLM 服务在 K8s 上的基本编排
apiVersion: apps/v1
kind: Deployment
metadata:
  name: llm-qwen35
  labels:
    app: llm-qwen35
spec:
  replicas: 2
  selector:
    matchLabels:
      app: llm-qwen35
  template:
    metadata:
      labels:
        app: llm-qwen35
    spec:
      containers:
        - name: vllm
          image: vllm/vllm-openai:latest
          args:
            - "serve"
            - "Qwen/Qwen3.5"
            - "--served-model-name"
            - "qwen3.5"
            - "--gpu-memory-utilization"
            - "0.9"
          ports:
            - containerPort: 8000
          resources:
            limits:
              nvidia.com/gpu: 1
              memory: "64Gi"
          readinessProbe:
            httpGet:
              path: /v1/models
              port: 8000
            initialDelaySeconds: 300
          livenessProbe:
            httpGet:
              path: /health
              port: 8000
            initialDelaySeconds: 600
```

```yaml
# service.yaml：暴露服务并配合 Knative/Istio 做弹性伸缩与流量治理
apiVersion: v1
kind: Service
metadata:
  name: llm-qwen35
spec:
  selector:
    app: llm-qwen35
  ports:
    - port: 80
      targetPort: 8000
```

> [!tip] 端侧部署替代方案
> 消费级硬件或对隐私敏感的场景，可用 llama.cpp 加载 GGUF 权重本地起服务：
> ```bash
> ./llama-server -m model.gguf --host 0.0.0.0 --port 8080 -ngl 99
> ```
> 它同样提供 OpenAI 兼容接口，适合原型验证与离线部署。

## 五、最佳实践与常见坑

**最佳实践**

1. **先压测、后上线**：用贴近真实负载的并发与序列长度压测 TTFT（首 token 延迟）与 TPOT（每 token 延迟），再决定引擎与参数。
2. **统一用 OpenAI 兼容接口**：对上游屏蔽底层引擎，降低多供应商迁移成本，也便于网关统一鉴权、限流与计量。
3. **分离性能与治理**：推理引擎管性能，KServe/Knative 管生命周期与弹性，Istio/网关管流量治理，职责清晰、各自可独立替换。
4. **显存预算显式化**：权重、KV cache、激活值都要算进显存；用 `--gpu-memory-utilization` 等参数显式预留余量，不要默认拉满。
5. **上可观测性**：对延迟、错误率、吞吐、KV cache 命中率设置指标与告警，配合 tracing 定位问题。
6. **锁定版本**：推理引擎与编排框架破坏性变更频繁（如 vLLM Model Runner V1 移除、SGLang 收紧 Python 版本、TensorRT-LLM 架构迁移），生产环境务必锁定版本并做好迁移预案。

**常见坑**

| 现象 | 可能原因 | 对策 |
| --- | --- | --- |
| 显存不足（OOM） | 模型过大、KV cache 膨胀、量化方案不当 | 降量化（FP8/NVFP4）、降上下文长度、开启 KV cache 量化与前缀缓存 |
| 延迟忽高忽低 | 长 prompt 阻塞短请求、批处理与缓存命中差 | 启用分块预填充与前缀缓存，调整 `max-num-seqs` |
| 启动报错、接口不兼容 | 升级到含破坏性变更的版本 | 核对 Python/CUDA/transformers 版本，回退或按迁移说明调整 |
| 并发一高就排队 | 未做弹性伸缩、副本数不足 | 用 Knative 自动伸缩，按吞吐目标规划副本与 GPU |
| 量化后效果明显劣化 | 把权重量化与 KV cache 量化混为一谈 | 分开评估，KV cache 需独立验证精度 |
| 多轮对话出现安全风险 | 缺少对话级监控与策略执行 | 引入网关限流、内容安全与对话级监控 |

## 六、核心要点速查

1. 服务化本质：把模型权重变成低延迟、高吞吐、可弹性伸缩、可用标准协议调用的在线服务。
2. 推理加速三基石：KV Cache + PagedAttention、连续批处理、分块预填充与前缀缓存。
3. **权重量化与 KV cache 量化是两条独立线**，只压权重不等于整体显存下降。
4. 并行路线：TP/PP/EP/CP，MoE 用 EPLB 均衡专家负载；大集群用 PD 分离优化资源。
5. vLLM 是通用生产默认，SGLang 适合高前缀重叠负载，TensorRT-LLM 适合 NVIDIA 全栈深度优化。
6. vLLM 标准启动方式是 `vllm serve`，旧的入口模块已弃用。
7. 生产化四件套：容器 + K8s 编排、OpenAI 兼容接口、鉴权限流计量、可观测性。
8. 版本迭代快，「最新」必须带日期；预发布版不可当稳定版用；生产锁定版本。
9. 选型看真实负载的压测数据，脱离负载谈吞吐没有意义。
