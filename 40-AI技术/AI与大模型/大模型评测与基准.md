# 大模型评测与基准

> [!summary] 摘要
> 本文系统梳理「大模型评测与基准」这一知识点：从**为什么需要独立评测**讲起，覆盖评测的基本概念、主流基准的适用边界、评测工具链的运行机制，以及从定义指标到落地评测的完整实践步骤。重点解决两个高频误区——**把榜单分数当作唯一选型依据**、**跨版本/跨设置直接比较分数**。适合需要为模型选型、提示词迭代、上线回归建立量化对照的工程师与研究者。本知识点在体系中位于 [[AI与大模型-从入门到精通]] 的「评估闭环」环节，与微调、推理优化、RAG 等知识点衔接。

## 一、最新动态（截至 2026-11）

> [!info] 说明
> 以下事实以调研文件为准，版本与工具状态随社区迭代变化较快，未在调研文件中确认到具体版本号的条目一律标注「以官方仓库为准」。

- **主流基准格局稳定，但区分度受质疑**：截至 2026-11，知识、推理、代码等方向的主流基准仍为 **MMLU、GSM8K、GPQA、MMLU-Pro、HellaSwag、ARC、HumanEval、LiveCodeBench、SciCode** 等。已有研究指出，HELM 与 Open LLM Leaderboard 在 MMLU 等任务上**排名区分度有限**，说明高分并不等于实际场景更强。
- **评测工具链**：EleutherAI 的 [lm-evaluation-harness](https://www.morphllm.com/llm-eval-harness) 仍是最通用的开源评测入口，**支持 200+ 任务、可接 vLLM 加速**；Stanford 的 **HELM** 提供更系统的多维评测；Hugging Face 的 **Open LLM Leaderboard v2 已归档**，不再作为活跃榜单使用（具体任务与版本支持以官方仓库当日状态为准）。
- **数据污染问题持续受到关注**：榜单训练集泄漏会虚增分数，评测结果必须结合**版本、few-shot 设置与评测时间**解读，不可跨版本直接比较。
- **框架侧的评估能力在加强**：LangChain / LangGraph 生态将 **LLM-as-judge 评估**、可观测性与回归检测纳入生产流程，成为上线后的常规动作。

## 二、基础概念

**大模型评测（Evaluation）** 是指用一组**可量化、可复现的指标**，衡量模型在特定任务、数据与约束下的实际表现，从而为模型选型、提示词/微调迭代、上线回归提供客观对照。它与「测试（Testing）」的区别在于：评测强调**横向可比**与**持续追踪**，而非一次性的单点验证。

几个必须分清的核心概念：

- **基准（Benchmark）**：一组标准化的数据集与任务，附带既定的评测协议。例如 MMLU 考多领域知识、GSM8K 考小学数学推理、HumanEval 考代码生成。
- **指标（Metric）**：把模型输出映射为数值的规则，如准确率、精确匹配（EM）、F1、pass@k。同一基准可以有不同指标口径。
- **评测协议（Protocol）**：few-shot 数量、提示模板、解码参数（温度、top-p）、最大生成长度等。**协议不同，分数不可直接比较。**
- **评测集与污染（Contamination）**：若评测数据出现在训练语料中，分数会被虚高。区分「干净集」与「污染集」是结果可信度的前提。
- **评测维度**：能力类（知识/推理/代码/数学）、安全对齐类、效率类（延迟、吞吐、显存）、质量类（对话、指令遵循）。选型不能只看能力分数。

> [!note] 核心认知
> **评测的本质是建立可复现的对照基线**。没有测试集与基线，任何「感觉变好了」的判断都无法沉淀为工程资产。

## 三、核心机制

**1. 任务类型与基准的对应关系**

| 能力方向 | 代表基准 | 典型指标 | 评测注意点 |
| --- | --- | --- | --- |
| 知识 | MMLU、MMLU-Pro、GPQA | 准确率 | 领域覆盖、few-shot 设置、污染 |
| 推理 | GSM8K、ARC、HellaSwag | 准确率 | 思维链提示对结果影响大 |
| 代码 | HumanEval、LiveCodeBench、SciCode | pass@k | 执行环境、测试用例口径 |
| 对齐与安全 | 安全/红队数据集 | 拒绝率、攻击成功率 | 多轮场景更接近真实风险 |

**2. 评测工具链的运行机制**

- **lm-evaluation-harness**：以「模型适配器（model）+ 任务（task）+ 采样参数」为核心。它负责加载模型、按统一协议构造提示、运行生成、计算指标，从而把「协议差异」这一最大噪声源标准化。支持接入 vLLM 等后端以加速批量评测。
- **HELM**：面向**多维、多场景**评测，除单任务分数外，关注一致性、效率与行为层面的指标，适合做更全面的模型体检。
- **LLM-as-judge**：用强模型对弱模型的输出进行打分，适用于开放式问答、摘要、指令遵循等**无标准答案**的场景。它引入新的偏差来源（偏好、长度、语气），需要用对照集与人工抽检校准。

**3. 评测流水线**

```
定义目标 → 选基准/建测试集 → 固定协议 → 跑基线 → 迭代改动 → 同协议重跑 → 对比差异 → 人工复核
```

其中「固定协议并重复跑」是保证结果可复现、可回归的关键一步。

## 四、实践步骤（含代码/命令示例）

**步骤 1：环境准备与工具安装**

```bash
# 推荐 Python 3.11+，使用虚拟环境隔离依赖
python -m venv .eval-env
# Windows
.eval-env\Scripts\activate
# Linux/macOS
# source .eval-env/bin/activate

pip install lm-eval
# 若需加速批量评测，可安装 vLLM（对齐调研文件 v0.34.0 的推荐版本）
pip install "vllm>=0.34.0"
```

**步骤 2：用 lm-evaluation-harness 跑标准基准**

```bash
# 本地 Hugging Face 模型，跑知识与推理基准
lm_eval \
  --model hf \
  --model_name Qwen/Qwen2.5-7B-Instruct \
  --tasks mmlu,gsm8k,hellaswag \
  --num_fewshot 5 \
  --batch_size 8 \
  --output_path ./eval_results

# 用 vLLM 后端加速（适合较大模型或批量评测）
lm_eval \
  --model vllm \
  --model_name Qwen/Qwen2.5-7B-Instruct \
  --tasks gsm8k,humaneval \
  --num_fewshot 5 \
  --output_path ./eval_results_vllm
```

**步骤 3：用 HELM 做多维评测**

```bash
helm run \
  --models openai/gpt-4o-mini \
  --datasets hellaswag,mmlu \
  --configs lm_harness \
  --limit 100 \
  --output_path ./helm_results
```

> [!note] 版本提示
> HELM 与 lm-evaluation-harness 的具体任务名、参数随版本变化，上述命令中的任务名与参数请以官方仓库当日文档为准。

**步骤 4：自定义评估脚本（LLM-as-judge + 准确率）**

```python
from langchain_openai import ChatOpenAI
import json, os

# 1. 待评估的模型输出（示例：同一道题的两个候选答案）
candidates = [
    {"id": 1, "answer": "42"},   # 与参考答案一致
    {"id": 2, "answer": "7"},    # 错误
]

# 2. 固定评测协议，避免分数漂移
judge = ChatOpenAI(model="gpt-4o-mini", temperature=0, max_tokens=200)

def score(answer: str, reference: str) -> float:
    """精确匹配：直接比对归一化后的文本。"""
    return 1.0 if answer.strip().lower() == reference.strip().lower() else 0.0

# 3. 简单准确率基线
reference = "42"
acc = sum(score(c["answer"], reference) for c in candidates) / len(candidates)
print(f"exact_match accuracy: {acc:.2f}")

# 4. LLM-as-judge：用于无标准答案的开放任务
prompt = (
    "请判断候选回答相对参考答案的正确性，"
    "只输出 JSON：{\"score\": 0或1, \"reason\": \"简要理由\"}。\n"
    f"参考答案：{reference}\n候选回答：{candidates[0]['answer']}"
)
raw = judge.invoke(prompt).content
print(json.loads(raw))
```

**步骤 5：把评测纳入 CI 回归**

## 五、最佳实践与常见坑

**最佳实践**

- **先定义成功指标，再动手调优**：明确要优化什么（准确率、格式合规、延迟、安全），再选择基准与测试集。
- **固定协议并记录元信息**：把模型版本、基准版本、few-shot 数、提示模板、解码参数、评测日期一并存档，这是结果可复现的前提。
- **维护基线版本**：保留改动前的评测结果（如 `baseline.json`），每次改动后同协议重跑、做差量对比，避免「凭感觉」判断。
- **检索与生成分开评估**（RAG 场景）：为检索单独设 SLO（如 p95 检索延迟、recall@k），而不是只看最终回答质量。
- **人工抽检校准自动评分**：LLM-as-judge 至少按固定比例抽人工复核，防止评分偏好系统性失真。

**常见坑**

| 现象 | 原因 | 对策 |
| --- | --- | --- |
| 分数高但实际场景差 | 榜单区分度有限、任务与业务不匹配 | 用贴近真实业务的测试集补充评测 |
| 跨版本分数无法比较 | 基准版本、few-shot、解码参数不一致 | 固定协议与元信息，同条件对比 |
| 分数异常偏高 | 评测数据污染 | 使用干净集、核查数据来源 |
| 开放任务评分失真 | LLM-as-judge 偏好长度/语气 | 人工抽检、双模型交叉评分 |
| 评测成本过高 | 每次全量重跑 | 抽样评测、固定评测集、后端加速 |
| 只看能力分数 | 忽略安全与效率 | 增加对齐、延迟、吞吐维度 |

> [!warning] 关键提醒
> **榜单分数不是选型结论，只是初筛线索。** 性能与质量数字高度依赖负载形状与评测设置，脱离自身场景直接照搬榜单数字会得出错误结论。

## 六、核心要点速查

1. 评测的本质是建立**可复现、可回归的对照基线**，不是一次性打分。
2. 基准分能力维度：知识（MMLU/MMLU-Pro/GPQA）、推理（GSM8K/ARC/HellaSwag）、代码（HumanEval/LiveCodeBench/SciCode）。
3. **协议（few-shot、提示模板、解码参数）不同，分数不可直接比较**，引用时必须注明。
4. 三大工具：**lm-evaluation-harness**（200+ 任务、可接 vLLM）、**HELM**（多维评测）、**LLM-as-judge**（开放任务自动评分）。
5. 榜单存在**区分度有限**与**数据污染**问题，高分不等于实际场景更强。
6. 评测流水线：定义目标 → 选基准 → 固定协议 → 跑基线 → 改动 → 同协议重跑 → 对比。
7. 开放任务用 LLM-as-judge，但必须**人工抽检**校准其偏好偏差。
8. RAG 场景中检索质量与生成质量**分开评估**，并设独立检索 SLO。
9. 把评测纳入 CI，作为改动的**回归门禁**。
10. 版本号与任务支持以**官方仓库/文档当日状态为准**，不要写绝对化表述。
