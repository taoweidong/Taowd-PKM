# 前端性能优化体系

> [!摘要] 摘要
> 本文是「前端性能优化体系」的系统化学习文档：以 **Core Web Vitals** 三大真实用户指标（**LCP / INP / CLS**）为度量基线，梳理**加载优化、运行时优化、渲染与状态优化、构建优化**四条主线，并落到 Vue3 框架侧可执行的优化手段与完整实践步骤。定位为 [[Vue3与前端-从入门到精通]] 体系下「从会看指标到能建立性能基线、持续回归」的落地手册。

## 一、最新动态（截至 2026-11）

- **Vue 进入双轨期**：稳定线为 **Vue 3.5.45**（2026-11-05 发布）；**Vue 3.6.0-rc.1**（2026-07-17）进入 RC，核心是 **Vapor Mode 功能完成** 与 **`@vue/reactivity` 基于 alien-signals 的响应式重构**，性能与内存显著改善，但截至 2026-11 **仍未进稳定版**，官方建议仅用于性能敏感页面局部使用或小型新应用。
- **构建工具 Rust 化收敛**：**Vite 8.0**（2026-03-12）以 **Rolldown**（Rust）取代 esbuild + Rollup 双打包器，配合 Oxc 与 Lightning CSS，官方称构建提速 **10–30×**，带来模块级持久缓存与更灵活的代码分割。
- **SSR 框架服务端无关化**：**Nuxt 4.6.0**（2026-10-05）引入 `nuxt/server` 与可移植 `RequestEvent`，并以 interop 模式支持 Vue Vapor；**Nuxt 3 已于 2026-07-31 停止支持（EOL）**。
- **交互指标定版**：**INP（Interaction to Next Paint）自 2024-03-12 起取代 FID** 成为唯一的交互性指标，FID 已于 2024-09-09 从 CrUX / PageSpeed Insights 移除。
- **TypeScript 原生化**：**TypeScript 7.0**（Go 原生移植，2026-07-08 GA），官方称约 10× 提速，但不再提供 JS 端编译器 API，影响部分工具链，详见 [[TypeScript与Vue3集成]] 相关风险提示。

## 二、基础概念

性能优化不是「把代码写快」，而是**让真实用户感知到的加载、交互、稳定性达标**。整个体系建立在三层认知上：

**1. 度量基线：Core Web Vitals（2026 阈值）**

| 指标 | 含义 | 好 | 待改进 | 差 |
| --- | --- | --- | --- | --- |
| **LCP**（Largest Contentful Paint） | 最大内容绘制时间，衡量首屏加载 | ≤ 2.5s | 2.5–4.0s | > 4.0s |
| **INP**（Interaction to Next Paint） | 交互到下一帧绘制，衡量交互响应 | ≤ 200ms | 200–500ms | > 500ms |
| **CLS**（Cumulative Layout Shift） | 累计布局偏移，衡量稳定性 | ≤ 0.1 | 0.1–0.25 | > 0.25 |

评估取**真实用户数据（CrUX）的 75 分位**，在**页面级与源级**两个维度评估。

**2. 实验室数据 vs 真实用户数据**：Lighthouse 是**实验室**工具，反映受控环境下的上限；CrUX 是**真实用户**数据，反映线上实际体验。两者结合使用：开发期用 Lighthouse 做回归，线上用 CrUX 验证。

**3. 三条优化主线**：
- **加载优化**：让首屏资源更快到达、更快执行，对应 LCP。
- **运行时优化**：让交互与滚动更流畅，对应 INP。
- **稳定性优化**：避免内容跳变，对应 CLS。

## 三、核心机制

**1. 关键渲染路径（Critical Rendering Path）。** 浏览器按「解析 HTML → 构建 DOM / CSSOM → 生成渲染树 → 布局（Layout）→ 绘制（Paint）→ 合成（Composite）」推进。**CSS 阻塞渲染、JS 阻塞解析**：任何阻塞渲染的 CSS 或同步 JS，都会推迟首次绘制与 LCP。优化方向是「尽早交付首屏所需资源，推迟其余内容」。

**2. 资源加载与优先级。** 浏览器按优先级排队加载资源，可通过 **资源提示（Resource Hints）** 提前建立连接或预取：`preconnect`（提前完成 DNS/TLS/TCP）、`dns-prefetch`（仅解析 DNS）、`preload`（高优先级预取关键资源）、`prefetch`（低优先级预取下一导航资源）。图片可用 `fetchpriority="high"` 提升 LCP 优先级，用 `loading="lazy"` 延迟非首屏图片。

**3. 压缩与传输。** 文本资源使用 **Brotli / gzip**（Brotli 压缩率通常更高），HTTP/2 支持多路复用与头部压缩，配合 **CDN** 缩短物理距离，可显著降低传输时间。

**4. 运行时事件循环。** JS 单线程，长任务会阻塞主线程、拖慢交互（INP）。拆分长任务、用 `requestIdleCallback` 把非关键工作安排到空闲帧，避免**布局抖动（layout thrashing）**——即「先读布局属性、再写样式」交替触发强制同步布局。

**5. Vue 响应式与渲染机制（框架侧性能底座）。** Vue3 用 **Proxy** 实现响应式，配合**依赖收集（`track`）/ 触发（`trigger`）**与 `effect`。3.5 起响应式核心用**版本计数 + 双向链表跟踪**重写并优化数组追踪，内存与更新性能改善；3.6 进一步基于 alien-signals 重构。编译期则通过**静态提升、Block Tree、补丁标记（PatchFlags）、事件监听缓存**减少运行时 diff 开销。

## 四、实践步骤（含代码/命令示例）

**步骤 1：建立度量基线。** 先用工具看清现状，再谈优化。

```bash
# 查看构建工具最新稳定版本（版本号以官方仓库为准）
npm view vite version
npm view vue version

# 用 Lighthouse 跑一次实验室基线，并直接打开报告
npx lighthouse https://example.com --preset=desktop --view
```

**步骤 2：加载优化——加资源提示、优先首屏。**

```html
<head>
  <!-- 提前与 CDN 建立连接，降低首屏网络握手耗时 -->
  <link rel="preconnect" href="https://cdn.example.com" crossorigin>
  <link rel="dns-prefetch" href="//cdn.example.com">
  <!-- 关键首屏样式与字体：高优先级预取 -->
  <link rel="preload" href="/assets/app.css" as="style">
  <!-- 首屏大图：不延迟，且提升优先级（LCP 图片不得 lazy） -->
  <img src="/hero.webp" fetchpriority="high" decoding="async" alt="首屏主图">
  <!-- 视口外图片：延迟加载，节省首屏带宽 -->
  <img src="/below.webp" loading="lazy" decoding="async" alt="次屏配图">
</head>
```

**步骤 3：构建优化——代码分割与手动分块（Vite 8 / Rolldown）。**

```javascript
// vite.config.js
export default {
  build: {
    rollupOptions: {
      output: {
        // 将体积大的第三方依赖拆成独立 chunk，利用长缓存
        manualChunks: {
          vendor: ['vue', 'vue-router', 'pinia'],
          echarts: ['echarts']
        }
      }
    }
  }
}
```

配合 Vite 8 的**模块级持久缓存**与 Tree Shaking，控制首屏 JS 体积；生产环境给带哈希的文件名设置长缓存，HTML 则不做长缓存：

```nginx
location ~* \.(js|css|png|woff2)$ {
  expires 1y;
  add_header Cache-Control "public, immutable";
}
location / {
  add_header Cache-Control "no-cache";
}
```

**步骤 4：Vue 渲染与状态优化。**

```vue
<script setup lang="ts">
import { ref, computed, shallowRef, markRaw, toRefs } from 'vue'

// 大对象不做深层代理：跳过响应式，避免无谓的依赖追踪
const bigList = shallowRef<Item[]>([])
// 无需响应式的重对象用 markRaw 标记，防止被代理化
const chart = markRaw(new HeavyChart())
const keyword = ref('')

// 派生状态用 computed，带缓存，避免模板里重复计算
const filtered = computed(() =>
  bigList.value.filter((i) => i.name.includes(keyword.value))
)
</script>

<template>
  <!-- v-memo 缓存列表子树，仅在依赖变化时更新 -->
  <div
    v-for="(item, i) in filtered"
    :key="item.id"
    v-memo="[item.id, keyword.value]"
  >
    {{ item.name }}
  </div>
</template>
```

**步骤 5：运行时优化——拆分长任务。**

```javascript
function scheduleIdle(task: () => void) {
  if ('requestIdleCallback' in window) {
    return requestIdleCallback(task, { timeout: 1000 })
  }
  return setTimeout(task, 1)
}

// 非关键渲染（如埋点、图表初始化）挪到空闲帧，避免阻塞交互
scheduleIdle(() => renderChart())
```

**步骤 6：度量与回归——用 Performance API 采集真实指标。**

```javascript
// 采集 LCP
const [lcpEntries] = await performance.getEntriesByType('largest-contentful-paint')
console.log('LCP =', lcpEntries.at(-1)?.startTime)

// 采集首屏导航耗时
const nav = performance.getEntriesByType('navigation')[0]
console.log('DOMContentLoaded =', nav.domContentLoadedEventEnd)
```

## 五、最佳实践与常见坑

**最佳实践**

- **先度量再优化**：用 DevTools Performance、Lighthouse、CrUX 定位瓶颈，避免凭感觉改代码。
- **首屏只留必需资源**：路由与组件**懒加载**，配合 `<Suspense>` 拆包，控制首屏 JS 体积。
- **稳定性优先**：为图片/视频预留**尺寸匹配的占位**，用骨架屏替代空白，直接降低 CLS。
- **长列表虚拟化**：数据量大时用虚拟滚动，避免渲染数万 DOM 节点。
- **合理使用缓存**：带哈希的静态资源长缓存，HTML 短缓存或不缓存，避免更新不生效。

**常见坑**

| 现象 / 写法 | 问题 | 处理 |
| --- | --- | --- |
| 首屏大图加 `loading="lazy"` | 延迟 LCP 图片，首屏变慢 | LCP 图片改用 `fetchpriority="high"`，仅对视口外图片 lazy |
| 同一节点上 `v-if` 与 `v-for` 同层 | 每次渲染都重新判断，列表更新浪费 | 用 `<template v-for>` 包裹，或先过滤后遍历 |
| 解构 `reactive` 对象 | 解构出的是普通值，丢失响应性 | 用 `toRefs` 展开，或改用 `ref` / `computed` |
| 滥用 `deep: true` 的 `watch` | 深度遍历放大开销，易造成卡顿 | 精确指定依赖，避免无必要的 deep watch |
| 读写布局属性交错 | 触发强制同步布局，造成布局抖动 | 批量写样式，读操作集中在写之前 |
| 过度使用 `preload` | 抢占关键资源带宽，反而拖慢首屏 | 只对首屏关键资源 preload，其余用 `prefetch` |
| 在 Vapor 组件中用 `v-memo` | Vapor 目前不支持 `v-memo` | 该场景改用其他渲染优化手段 |
| 盲目启用 Vapor Mode | 3.6 仍处 RC、非稳定 | 仅在性能敏感页面局部试跑，可回滚 |

## 六、核心要点速查

1. 三大真实用户指标：**LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1**，取 CrUX **75 分位**，按页面级与源级评估。
2. **INP 是唯一的交互性指标**，2024-03-12 起取代 FID。
3. 加载优化四件套：**资源提示（preconnect/dns-prefetch/preload/prefetch）、压缩（Brotli/gzip）、HTTP/2、CDN**。
4. **LCP 图片不得延迟**，用 `fetchpriority="high"`；非首屏图片才用 `loading="lazy"`。
5. 运行时优化：**拆分长任务**、`requestIdleCallback`、避免**布局抖动**、长列表**虚拟化**。
6. 稳定性：尺寸匹配的占位 + 骨架屏，直接压降 CLS。
7. Vue 侧：**`shallowRef`/`shallowReactive` 跳过深层代理**、`markRaw` 防代理、`toRefs` 保响应性、`computed` 做派生、`v-memo` 缓存列表子树。
8. 渲染侧：稳定 `key`、组件**异步化 + `<Suspense>`**、`<KeepAlive>` 缓存、避免大组件无谓重渲染。
9. 构建侧：**Vite 8 / Rolldown** 的代码分割、Tree Shaking、模块级持久缓存、手动分块与长缓存。
10. 度量工具：**Performance Web API、Lighthouse（实验室）、CrUX（真实用户）、Chrome DevTools**。
11. 框架底座：Vue **3.5.45 稳定**；**3.6.0-rc.1 的 Vapor + alien-signals** 性能更优但仍处 RC，生产需锁定 3.5.x。
